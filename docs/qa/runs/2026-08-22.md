## What failed first, and what it meant

Two procedures failed on the first run. Neither was a flaky test; both said something true.

**QA-2.4 — "a red banner containing *not an email address*"** produced a different message.
`NewContactRequest` carried `@Email`, so Jakarta validation rejected the address before the
domain ever saw it, and the user was told a framework's sentence instead of the domain's.
Two definitions of what an email address is, in two layers, free to disagree. The annotation
was removed: presence and length are shape, validity is the domain's business. The API test
now pins the domain's wording as part of the contract.

**QA-6.5 — "the Lead total returns to what it was"** failed twice, for two different reasons,
and both were the procedure's fault rather than the product's:

1. The first version asserted the literal figure `777,000`. The forecast line is a **total**
   over every open deal in that stage, and the demo database is shared — so it only passed on
   an empty database. Rewritten to measure the *difference*, which is what the rule actually
   says.
2. The rewrite then read the table before the new grouping had arrived, because it waited for
   the dropdown it had just changed rather than for the server's answer. The forecast heading
   now carries `data-testid="forecast-grouping"` and is rendered **from the response**, so
   waiting for it means waiting for the data. A script that waits for its own input is not
   waiting for anything.
